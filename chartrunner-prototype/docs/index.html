ChartRunner SDK v1.0.943

A gamified trading SDK on Solana, built on three pillars — gamification, education, on-chain (industry-standard). 17 in-game SDK primitives (bracket, OCO, ladder, hedge, radar, rescue, and 11 more), four Anchor programs live on devnet, and adapters for three further protocols — Phoenix, MagicBlock, Honeycomb — that are built but carry no traffic: no order, no match and no mint is routed through any of them, and none of it is dated. Trades in the game are simulated by default; live trading is an optional, self-custodial opt-in that routes through Jupiter on Solana mainnet (market orders and resting limit orders, 0.5% platform fee, every transaction signed by your own wallet).
Two minutes from cold start to running a chart. Wallet-first login → on-chain leaderboard → real Solana RunRecord PDAs written from inside the game (devnet). Every primitive learned in the game is the same SDK call shape you'd run in production. The primitive shapes themselves execute against the simulator; real execution today is the opt-in Jupiter route (market + resting limit orders on Solana mainnet).

Overview

ChartRunner is a gamified trading SDK that lets new traders learn through play. Each in-game gesture (a bracket, an OCO, a ladder fill) maps 1:1 to an SDK call shape that lives in production. The runtime composes:

  • A canvas game — an HTML prototype that runs on real chart candles, with bear monsters, an upside-down world, and 17 trading primitives wired as in-game abilities.
  • An on-chain layer — four Anchor programs (maps · registry · match · oracle), all live on devnet under a Squads V4 2-of-3 multisig.
  • Services that are in service — a money worker (Pro and Boost checkout), a tx worker that builds trade transactions and never signs, an own candle store, an ownership register, and a rooms server for live multiplayer. These carry the real traffic; see Endpoints.
  • Three ecosystem adapters — trades (Phoenix Rise), matches (MagicBlock Ephemeral Rollups), economy (Honeycomb). All built; execution is not yet enabled. The fourth, price truth (Pyth), was removed on 2026-09-20 — as a price source and as a partner. Only our own devnet program chartrunner_oracle remains.

Phoenix intent · nothing built beyond the adapter

Phoenix is an intention, not a component. Phoenix is meant to become the second trading venue beside Jupiter, and the reason for wanting it is perpetuals. Nothing of that is built: no order is routed to Phoenix, no perpetual position can be opened anywhere in this product, and there is no date. What exists is an adapter file that maps each in-game primitive onto a Phoenix order shape, wrapped with the Phoenix Flight builder layer. The call shape below is a target API.

If perpetuals arrive, leverage arrives with them. Today the worst case on a live ChartRunner trade is a bad price: you swap what you hold, for less than you hoped. A perpetual is a different instrument — it is margined, so a position can be liquidated and a player can lose the collateral behind it, not just the spread. That is the part that has to be said in the same breath as the word "perpetuals", and it is the part a game surface makes easiest to forget.
No numbers here, on purpose. This page states no fee, no leverage cap, no market list and no collateral rule for Phoenix. The 0.5% ChartRunner charges on the quote side of a Jupiter swap does not carry over: perpetuals are priced as maker and taker fees on notional, plus funding, and whether an integrator share exists there at all is open. Any number written here today would be invented.

Note on packages: the spot path would be the Phoenix legacy spot CLOB via @ellipsis-labs/phoenix-sdk; Phoenix perpetuals are in closed beta and have no public adapter package to pin — which is also why the perpetual half cannot be built today even if it were scheduled.

MagicBlock Ephemeral Rollups intent · program on devnet, matchmaking not wired

Two players running on the same chart with every move settled on-chain isn't possible at Solana's base-layer 400 ms slot times. Ephemeral Rollups are the intended solution for the on-chain version of that — the MatchState PDA delegates to MagicBlock's ER validator, where every player's tick_player settles in ~1 ms at zero fee, committing state back to base layer every 30 s. The chartrunner_match program is deployed on devnet and the adapter is built, but matchmaking, the PvP UI, and anti-cheat on tick_player are not yet wired — scores are self-reported until anti-cheat lands, so no ranked PvP runs live today.

Multiplayer does run today — just not this one. Live rooms are served by a standalone rooms server at wss://rooms.chartrunner.xyz, not by an Ephemeral Rollup, and nothing about them is on-chain. Since the rooms server reached v1.4.0 a room shares more than ghost runners:
  • Shared chart overlays — trendline, Fibonacci extension and anchored VWAP. What travels is the configuration (kind, anchors in time and price — never screen coordinates — parameters, token and timeframe); each client draws it itself. The server holds the state per room, sets the author from the connection, and hands a joiner the full state on arrival rather than only what happens after them.
  • A context lock. If the viewer's token or timeframe differs, the overlay is not drawn — a notice naming both is shown instead. Somebody else's line over your different candles would look like a signal and be a coincidence.
  • Other people's overlays are marked as such — dashed, carrying their author's name and colour, and not grabbable anywhere: no handle, no selection, no drag. A toggle in the tool menu hides them, and it appears only inside a room.
  • Moderation — mute/unmute and removal from a room, and a host is a host because the server says so, not because a client claims it.
  • No silent degradation. If the server does not advertise the overlay capability on created/joined, the client says so once, visibly, and falls back to the old anchor echo. A feature that quietly stops working is worse than one that is absent.

The under-told story — cross-game portability

A Honeycomb Character earned in ChartRunner is the same Character in any other Honeycomb-integrated Solana game. A Bronze trader in ChartRunner starts elevated in the next game on the network. We get that network effect for free by adopting Honeycomb's primitives instead of inventing our own. ChartRunner positions as the credentials engine for Solana-native trading skill — Honeycomb gets a flagship game with real trader pedigree on its Character schema; we get our Character to have utility outside our own product.

What remains is chartrunner_oracle — our own program, on devnet, described below. It implements the Pyth pull-oracle pattern and cites Pyth's receiver program; that is a dependency of a devnet artifact, not a live integration. This section used to be tagged "live integration"; it never was one.

chartrunner_oracle implements the Pyth pull-oracle pattern: it accepts a price update posted by the Pyth solana-receiver program, enforces a 30-second freshness gate, and writes a PriceCertificate PDA that chartrunner_registry::record_run can optionally cite. The design goal was that a forged score would require forging Pyth's signed VAA — the same security model as Pyth itself.

Why /health is documented at all. It is the one place where a service says, without being asked, what it is and which commit it runs. A merged pull request is not a rollout, and a green CI run is not a deployment — so "is the change live?" is only answerable if the service answers it. Where a worker names its commit it does so as git_sha at the top of the response.

/health is also a contract, not just a status line. The boost checkout in the game reads features.boost_checkout from the money worker — ok, a reason when not, the sellable tiers with their prices, and the unavailable ones with their reason. The client holds no price list of its own, and offers no payment at all unless that answer says it can sell (fail-closed). The trade path does the same: the resting-order flow preflights GET /health on the tx worker and reads endpoints, platform_fee.per_input_mint and trigger.resting_default from it rather than from constants.
Not complete, and that is the finding. Not every service can answer this yet. workers/account/ and workers/alerts-cron/ in this repo have no /health at all; workers/ownership/ has one, but it can only name its commit when GIT_SHA is injected at deploy — otherwise it answers git_sha: null plus a note saying it cannot name its own commit (workers/ownership/src/index.js:401-403). The gap is tracked, not papered over.

1.0.938The last hard-coded payment address is out of the product. Address, amount and reference now come exclusively from POST /v1/pay/sol/intent, polled via GET /v1/pay/sol/status?reference=…. No intent, no payment target — five visible states instead of a silent fallback, and a link with amount=0 is no longer constructible. The USD→SOL rate behind that amount is taken in the worker — Jupiter first, CoinGecko as the fallback, with an age limit on it — and if neither answers in time the result is a named error rather than an amount. A payment built on an invented rate is worse than a payment that does not happen. worker-side readable from the deployed worker, not from this repository.
